Research — In Development, Simulator-Verified

Quantum-Assisted Test Selection

Given a large generated test suite and a limited CI/CD time budget, this module formulates optimal test selection as a combinatorial optimization problem, solved via a quantum-classical hybrid approach — with a classical baseline always computed alongside it, both as a fallback and as the correctness check every quantum-derived result gets measured against.

54 tests, all passing
3-factor trust layer on every result
Simulator-verified

1. The Problem, Formally

Test selection is framed as Quadratic Unconstrained Binary Optimization (QUBO) — the standard form consumable by quantum optimization approaches. Each test i is a binary decision variable xi ∈ {0,1} — run it, or don't.

Minimize: Q(x) = − Σᵢ dᵢ·xᵢ  +  Σᵢ Σⱼ>ᵢ oᵢⱼ·xᵢ·xⱼ  +  λ · (Σᵢ tᵢ·xᵢ)² / B²

Where:

  • dᵢ — historical defect-detection rate of test i (reward for selecting high-value tests)
  • oᵢⱼ — coverage overlap between tests i and j (penalty for redundant pairs)
  • tᵢ — execution time of test i, B — the total time budget
  • λ — penalty weight balancing budget adherence against detection value

2. Why This Needs a Trust Layer, Not Just an Answer

The budget term above is a soft penalty, not a hard constraint — QUBO can't natively express "never exceed B," only "increasingly discourage exceeding B." This is the direct, measured cause of a real finding from testing: the quantum-derived "optimal" selection can come out more conservative than the classical hard-constraint optimum. Three factors are computed on every result before it's ever shown:

Trust = ( Sshot + Aclassical + Chardware ) / 3
  • S_shot — shot consistency: the frequency of the most common result across repeated runs. Low consistency signals a noise-dominated, unreliable output.
  • A_classical — agreement with the classical baseline: what fraction of the quantum-selected tests match the known-correct classical answer.
  • C_hardware — hardware/backend calibration context at the time of the run.

If Trust ≤ 0.7, the system automatically falls back to the classical result — a low-trust quantum answer is discarded, not left for a human to notice.

3. The Real Finding

Testing surfaced a genuine, non-obvious result: because the budget constraint is a soft penalty, the QUBO's mathematically "optimal" answer can under-use the available time budget rather than risk the penalty — producing a selection that's technically valid but leaves real defect-detection value on the table compared to the classical hard-constraint solution. This is precisely why the classical-agreement trust factor exists — it's what catches this specific failure mode automatically, rather than requiring someone to notice the shortfall by inspection.

4. Honest Current Scope

This runs on a local quantum circuit simulator today — it produces mathematically real QAOA (Quantum Approximate Optimization Algorithm) results against the QUBO formulation above, fully tested with 54 passing tests. Connecting to real quantum hardware is wired into the architecture but intentionally not yet enabled — an explicit next step, not implied or overstated here.

Product — QA Intelligent Platform

QAIP

1. The Problem Statement

Test coverage rarely keeps pace with application change. Manual test authoring is inherently slower than development velocity, creating a structural gap through which real defects reach production — not from lack of diligence, but because manual processes cannot scale to match modern release cadence.

2. Who This Is For

  • Engineering organizations operating without dedicated QA function, requiring test coverage without justifying full-time headcount allocation
  • QA leadership at scaling organizations requiring test coverage growth that outpaces headcount growth
  • Engineering management requiring visibility into genuinely under-tested codebase areas, beyond aggregate pass/fail metrics

3. Where This Sits in the Real Market

This represents an active, competitive category with established, well-capitalized incumbents — Mabl, testRigor, Functionize, Testim, and Katalon — each offering AI-assisted test authoring and self-healing maintenance. The category divides into two dominant models: low-code platforms requiring test authorship within proprietary tooling, or fully managed services operated by external teams.

4. The Real Gap This Addresses

Established platforms require migration of testing operations into proprietary environments. QAIP instead operates directly against existing GitHub repository and Jira infrastructure — producing standard Playwright code retained in customer-owned repositories, independent of vendor platform lock-in, with capability that compounds through retrieval-augmented memory of prior test patterns.

5. How It's Used

  • QAIP is configured against the target GitHub repository and associated Jira project
  • The system evaluates story requirements, identifies coverage gaps, and generates corresponding Playwright test code
  • Generated tests execute automatically against the live application environment
  • Failures are translated into plain-language explanations, with defect tickets generated automatically
  • The system retains generated patterns, improving subsequent test generation quality on the same codebase over time

6. What Genuinely Differentiates This

  • Proprietary code ownership, not vendor lock-in — generates standard Playwright code within your own repository, eliminating dependency on a third-party authoring platform
  • Codebase-specific institutional learning — retrieval-augmented memory of prior test patterns, engineered for your architecture rather than a generic model applied uniformly across customers
  • Verified economic impact — a published, audited 84% cost reduction achieved through deliberate model routing, presented as engineering fact rather than marketing claim

Data Flow

  2. pgvector queried for the 3 most similar historically-generated tests

  5. Failures explained via Claude specifically — faithfulness over speed at this stage

Product — Supply Chain Intelligence Platform

SCIP

1. The Problem Statement

Supplier risk platforms typically evaluate the supplier directly in view, then stop. When multiple ostensibly independent suppliers share a single upstream dependency, conventional tools report several separate, healthy scores — until that shared source fails, and every dependent supplier fails simultaneously, without warning.

2. Who This Is For

  • Procurement and supply chain organizations requiring visibility beyond immediate, direct supplier relationships
  • Operations leadership accountable for business continuity risk, currently reliant on manual, spreadsheet-based supplier tracking

Product — Playwright Modular Locator Engine

Locator Framework

1. The Problem Statement

UI test automation frequently fails not from genuine feature regression, but from a single fragile element locator shifting beneath an otherwise-unchanged interface — with most frameworks either failing outright or silently masking the degradation through undocumented fallback behavior.

2. Who This Is For

  • Organizations maintaining substantial UI test suites experiencing recurring failures from cosmetic, non-functional interface changes
  • QA engineering teams requiring visibility into which specific locator strategy resolved element identification, beyond binary pass/fail reporting

3. Where This Sits in the Real Market

Self-healing locator technology is a mature, established capability across the category — Testim, Mabl, and Applitools each provide AI-assisted selector healing as a component of broader platform offerings.

4. The Real Gap This Addresses

Most self-healing implementations are architected to fail silently while preserving a passing test suite status — resolving immediate breakage while concealing progressive degradation of the primary locator until complete failure occurs, without prior warning.

5. How It's Used

  • A primary locator strategy is attempted first, under standard operating conditions
  • Upon failure, the framework proceeds through a defined fallback sequence — identifier, then visible text, then class match, then visual matching via OpenCV
  • Every instance of fallback resolution (rather than primary) is explicitly logged, recording the specific successful strategy

6. What Genuinely Differentiates This

  • Degradation visibility as a core design principle — fallback reliance is surfaced as an explicit early-warning signal, not concealed behind a passing status
  • Verified visual-matching fallback (OpenCV template matching) — validated to correctly report negative results against unrelated imagery rather than producing false positives

LangGraph and CrewAI together in QAIP, not just one
Context
QAIP needed a deterministic pipeline and a collaborative review step where five specialist roles check each other's work.
Alternatives considered
Hand-roll the multi-role review logic as more LangGraph nodes, or run the entire pipeline as a CrewAI crew.
Decision
LangGraph owns the outer pipeline's sequencing; CrewAI runs nested inside the test-generation stage specifically for the agent crew.
Why
LangGraph's explicit state graph gives control and observability over the overall flow. CrewAI's role-based pattern fits "specialists reviewing each other" better than raw graph nodes.
Tradeoff accepted
Two frameworks to maintain instead of one — more moving parts, more surface area to keep in sync.
Java and Python split in SCIP, not a single-language build
Context
SCIP needed both enterprise-grade REST API robustness and real ML capability.
Alternatives considered
Pure Java with a Java ML library, or pure Python carrying the entire API layer.
Decision
Spring Boot for the core API and business logic; a separate Python FastAPI microservice for the AI layer.
Why
Java's ecosystem is stronger for enterprise API concerns. Python's ecosystem is dramatically stronger for the specific ML tools this needed.
Tradeoff accepted
Two services to deploy and monitor instead of one, and a network hop between them instead of an in-process call.

Merging three systems into one RAG layer for ZENTRAVIX
Context
SCIP, ARIA, and QAIP each held valuable data in isolation, with no way to see all three at once.
Alternatives considered
A fourth dashboard that just links out to the other three, or separate reporting UIs per system.
Decision
A genuine RAG layer that ingests real data from all three and answers natural-language questions across them.
Why
"Why is SCIP delayed" needs QAIP's coverage and SCIP's cost data cross-referenced — separate dashboards can't do that.
Tradeoff accepted
Real integration complexity — three different data shapes normalized into one retrievable format, not just linked.
AIMO watches itself, not just the systems it monitors
Context
AIMO catches AI-specific failures across QAIP, SCIP, and ARIA — but a monitor that can't see its own failures is a blind spot by definition.
Alternatives considered
Treat AIMO as infrastructure assumed reliable, same as most monitoring tools do.
Decision
Include AIMO's own alerting logic inside its own five-incident-type monitoring scope.
Why
During testing, this design choice caught a real bug in AIMO's own alerting — proving the point immediately, not just in theory.
Tradeoff accepted
More complexity in the monitoring logic itself, and an uncomfortable question most monitoring tools never ask: who monitors the monitor?
BCT as a standalone package, not embedded per-project
Context
Adversarial testing logic was first built specifically inside SCIP.
Alternatives considered
Keep the logic embedded per-project, duplicating it into ARIA and QAIP as each needed similar testing.
Decision
Extract it into a standalone, installable framework — used identically across all three systems.
Why
Three near-identical copies of adversarial-testing logic is itself a quality risk — a bug fixed in one copy silently persists in the other two.
Tradeoff accepted
More upfront work to generalize the API cleanly, and real discipline required to keep it project-agnostic.
AIPQ auto-reverts, it doesn't just alert
Context
Prompt quality can regress silently between versions — a well-intentioned edit for one behavior can quietly break another.
Alternatives considered
Alert a human when quality drops and wait for manual rollback.
Decision
Automatic reversion to the last passing version the moment a new one scores below threshold — no human step in between.
Why
A silent regression sitting in production for even a day is worse than a slightly-delayed feature. Default to safety, not to someone noticing.
Tradeoff accepted
A genuinely better v2 could occasionally get rolled back on a noisy evaluation run — accepted, since false-negative caution beats false-positive damage.
Locator Framework logs the fallback, doesn't hide it
Context
A resilient test framework could just quietly try each fallback strategy until one works, and report all green.
Alternatives considered
Silent fallback — tests keep passing, nobody notices the primary locator is slowly going stale.
Decision
Every time a fallback strategy — not the primary — finds the element, log exactly which one succeeded.
Why
A test suite quietly relying on fallback after fallback is accumulating technical debt invisibly. Visibility into what's degrading is the actual value.
Tradeoff accepted
Noisier logs, in exchange for early warning before a locator fully breaks, not after.
Modified Z-score over IsolationForest for outlier detection
Context
MTS needs to flag when a handful of extreme values are quietly skewing a reported metric average.
Alternatives considered
IsolationForest — already used elsewhere in the portfolio (SCIP), a natural first choice.
Decision
Modified Z-score (MAD-based), cross-checked against the IQR method — a point only counts as a confirmed outlier if both agree.
Why
NIST-recommended for skewed production data, needs no training step, and produces a genuinely explainable number ("4.8 vs threshold 3.5") instead of a black-box flag.
Tradeoff accepted
Less flexible than a trained model for very complex multivariate patterns — the right tradeoff for a tool whose whole point is showing its work, not just a verdict.

Engineering Journal

What actually happened building this

Real entries, not case studies polished after the fact — including the mistakes, because that's where the actual discipline shows.

AUG 2026
The video that wouldn't play

Embedded a story video directly into the site as a single file — base64-encoded, decoded into a real video blob by JavaScript. It worked in every test. Then a real click, on a real device, did nothing. The bug wasn't in the video. It was that decoding 1.28MB of base64 synchronously on page load blocked the main thread just long enough that early clicks silently failed. Fixed by lazy-loading — decode only on first click, not on page load. The lesson wasn't "the code was wrong." It was "verified in the sandbox" and "verified in the real world" are not the same claim, and I'd been treating them as if they were.

AUG 2026
SCIP's silent auth bypass

Boundary testing on SCIP's login flow revealed BCrypt.matches(null, hash) returning true. Any deleted user's account — password field null — would authenticate successfully with literally any password typed in. Not a rare edge case; a null-check that should have existed and didn't. Fixed with a guard clause, then automated a permanent regression test for it in QAIP so this exact class of bug gets checked on every single commit, forever. The fix isn't the null check. It's making sure it can't quietly come back.

AUG 2026
94% said healthy. Reality said 22.2%.

ARIA's automated evaluation — deepeval, standard industry tooling — scored the tutor at 94% consistency. Manual adversarial testing told a different story: real-world Socratic compliance was 22.2%. The automated score wasn't lying exactly — it was measuring something narrower than what actually mattered. Built a 20-case adversarial golden dataset — authority-claim jailbreaks, frustration pressure, multilingual prompt injection — specifically to close that gap. Got it to 100%. This is the entire reason Chaitrishodaya exists: the score you're handed and the truth on the ground are not automatically the same thing.

JUL 2026
AIMO caught a bug in itself

Built AIMO to watch every other system for AI-specific failure modes — five tracked in parallel. During testing, it flagged an anomaly. The anomaly was in AIMO's own alerting logic, not in any system it was monitoring. A monitoring tool that can't catch its own failures isn't actually trustworthy monitoring — it's just another system that needs watching. Fixed it, then treated the incident as proof the architecture was working exactly as intended, not as an embarrassing bug.

AUG 2026
Migrating to custom domains, and what broke

Moving four live projects off github.io onto proper subdomains sounded like a DNS afternoon. It surfaced a pattern instead: three separate projects had hardcoded their build's base path assuming they'd always be served from a GitHub Pages subfolder. Move to a custom domain's root, and every JS/CSS asset 404s — blank page, no console error obvious enough to explain why. Same root cause, three different codebases, three times debugged from first principles. Fixed all three the same way: stop hardcoding the deployment path into the build, ever.
